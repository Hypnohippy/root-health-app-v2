## Final pre-access clarification and local release checks

The introducer's commercial onboarding is already handled by Root Health's existing `/admin/introducers` system, including registration, commercial terms, contracts, and digital signatures. The demo must not duplicate those steps. Root-controlled provisioning must assign a fictional organisation with `status='demo'`, populate its fictional members and historical wellbeing data, map the existing access grant, and activate time-limited access last. Introducers must not create organisations, employees, agreements, or sample history.

Local code now refuses authorization unless the grant has a mapped `status='demo'` organisation, at least five employee memberships without real Auth-user links, and at least five distinct baseline participants. Demo state loading is read-only; reset removes new fictional check-ins without rebuilding or replacing Root-provisioned history. A Root-only Preview endpoint and deterministic, idempotent fictional customer-shaped seed process are now implemented locally. It checks the verified Root administrator, confirmed Auth user, existing active grant and absence of real organisation memberships; maps the grant only after the fictional organisation, units, workforce profiles, memberships, and history are upserted. Local test-double results do not prove the operation against live Preview, and the new customer-shaped fixture has not been applied there.

Introducer restrictions are limited to Vercel Preview deployments. Any `VERCEL_ENV=production` deployment is classified as the normal customer deployment before introducer project/database markers are considered. A future dedicated introducer Production deployment therefore needs a separate reviewed activation design. The optional audio-generation endpoint now checks `OPENAI_API_KEY` only when an authorized request reaches it and returns 503 if unconfigured; no credential is fabricated or exposed, and the production-equivalent build no longer needs that optional admin credential.

The authenticated introducer route now redirects from `/introducer` to the genuine Root home and exposes the existing Personal Root routes plus a constrained Workplace slice: `/org-insights`, `/executive-review`, and `/launch-kit`. `/hr-coach` is deliberately hidden and routed away because its current API still requires a real database HR membership. The grant-backed Root identity is a client navigation capability only; employer data still goes through server authorization and aggregation. Paid subscription and omitted employer-admin features are unavailable. The Preview has not passed live browser acceptance and must not collect real wellbeing data yet.

## Do not apply this export unchanged

The source database’s access configuration is not safe for the introducer environment:

- RLS is enabled on 43 of 45 tables. `journal_entries` and `mind_entries` have no RLS, while `anon` and `authenticated` have table grants.
- Several enabled tables still have blanket policies. In particular, `wellbeing_assessments` has public `SELECT` and unrestricted `INSERT`; `organisations` has unrestricted `SELECT` and `INSERT`; and `organisation_members` has unrestricted `SELECT`, `INSERT`, and `UPDATE`. `body_signals` has public anonymous read/insert policies. These policies allow access regardless of the intended introducer role.
- `voice_sessions` has a default-public policy keyed only on `profile_key = 'main'`.
- The dump grants table privileges to `anon` and `authenticated`, including on subscription, organisation, invitation, commercial, and personal-evidence tables.
- All 12 default-privilege statements grant `ALL` on future tables, sequences, or functions to `anon` and/or `authenticated`. The introducer baseline must revoke these defaults before creating application objects.
- There are 24 `SECURITY DEFINER` functions and none pins `search_path`. Nine are executable by `anon` or `authenticated`, including `redeem_organisation_setup_invite`, `transfer_organisation_admin`, `apply_confirmed_workforce_import`, `accept_workforce_invitation`, `list_workforce_invitations`, and `next_root_commercial_document_number`. Their grants and bodies must be individually reviewed; none should be exposed to introducers by default.

The presence of a policy is not evidence of adequate authorization. PostgreSQL combines permissive policies with OR semantics, so adding a restrictive-looking policy does not neutralize an existing `USING (true)` or `WITH CHECK (true)` policy. The isolated baseline must omit or explicitly remove the source policies and replace them with an allowlist.

## Grant-scoped HR bridge and Preview compatibility

The introducer branch of `/api/organisation/insights` now calls the existing introducer authorization guard, which verifies the bearer session, confirmed invited account, active non-revoked/unexpired grant, and exclusion of customer entitlements. The guard returns the grant's fixed `demo_organisation_id`; the endpoint rejects a mismatching caller-supplied organization before loading data. It skips the customer HR-membership check and does not invoke `organisation_workforce_context`. Instead, the existing Root aggregation engine receives a context calculated from the authorized fictional `organisation_members` and `organisation_units` records. The normal customer branch still uses customer HR membership and the existing RPC.

For the introducer response, optional roster rows omit email, Auth user ID, and profile key. Aggregate queries are server-side and filtered to the grant-mapped fictional organization; the existing suppression function remains in the path. The grant authorization helper now returns its mapped organization ID. Grant expiry/revocation is checked by that helper on each request and by the employer RLS policies. The already-applied baseline's personal policies were owner-scoped but did not independently check grant expiry/revocation.

The migration checks that the four expected introducer tables are the only public tables, all have RLS enabled, and that the reviewed existing columns are present. It refuses to proceed if any of the 16 customer-derived allowlist tables already exists. It only adds the nullable demo-organization mapping and FK to the existing grant table, then creates new allowlisted tables and replaces old policies on the four demo tables. It contains no `DELETE`, `TRUNCATE`, or drop-table operation. A local compatibility test applies the prior two introducer migrations, inserts synthetic grant/member/assessment/introduction rows, applies the baseline, and verifies all four rows remain and RLS stays enabled. It revokes future table and sequence defaults for objects created by `postgres` in `public`. It creates no functions and does not change global or schema-scoped function defaults; any later migration that introduces a function must explicitly revoke `EXECUTE` from `PUBLIC`, `anon`, and `authenticated` for that function.
